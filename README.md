# 배치 1 · 네이버 매물 수집 → 구글시트 『매물장』 적재

관심 단지의 매물을 수집해 구글시트 『매물장』에 전량 교체 적재하는 배치.
(분석·알림은 배치 2가 담당하며, 두 배치는 구글시트로만 이어진다.)

## 설치

```bash
pip install -r requirements.txt
```

> 2026-08-05부터 수집이 **API 직접 호출**로 바뀌어 브라우저가 필요 없다. 예전에 하던 `playwright install chromium`은 이제 필요 없다.

## 설정

`.env` 파일에 구글시트 연동 정보를 둔다 (저장소에 커밋하지 않는다).

```
GSPREAD_KEY_FILE=navercomplexnosearch-273fa9c1af10.json   # 서비스 계정 키파일 경로
SPREADSHEET_ID=...                                        # 대상 스프레드시트 ID (배치 2와 동일 문서)
CONFIG_SHEET=설정
MAEMULJANG_SHEET=매물장
WATCH_LABEL=감시단지
LOG_SHEET=실행로그                                          # 실행로그 탭
```

- 서비스 계정 이메일을 대상 시트에 **편집자로 공유**해야 한다.
- 실행로그 탭 이름을 바꾸면 `LOG_SHEET` 값도 함께 바꿔야 한다.

### 수집 속도 조절 (선택)

네이버는 요청이 몰리면 HTTP 429로 막는다. 기본값이 이미 보수적이라 평소엔 건드릴 일이 없다.
막히는 날이 잦아지면 `.env`에 아래를 넣어 조인다.

```
NAVER_REQUEST_DELAY=1.5      # 요청 간격(초). 늘리면 안전, 실행시간은 길어짐
NAVER_TEL_MAX_PER_RUN=20     # 회당 새로 받을 중개업소 전화 수. 0에 가까울수록 안전
NAVER_FETCH_OFFICE_TEL=1     # 0 이면 업소전화를 아예 안 받는다 (요청 수 최소)
NAVER_MAX_RETRIES=3          # 실패 시 세션 갱신 후 재시도 횟수
```

위 값은 **코드 기본값**이다. 현재 `.env`는 `NAVER_TEL_MAX_PER_RUN=10`으로 더 조여 두었다.
업소전화 캐시가 다 차면 이 상한에 걸릴 일이 없어지므로 **그대로 두면 된다.**

## 수집 방식과 요청량

수집은 `fin.land.naver.com`의 매물 API를 `httpx`로 직접 호출한다.

1. 단지 페이지를 한 번 열어 **세션 쿠키**(`PROP_TEST_KEY`/`PROP_TEST_ID`)를 받는다. 네이버 로그인은 필요 없다.
2. 매물 목록 API를 페이지 끝까지 호출한다. **단지당 1~2회**로 끝난다.
3. 업소전화만 목록에 없어 매물 상세를 따로 받는다.

3번이 전체 요청의 대부분이라, 전화는 **중개업소 단위로 `office_tel_cache.json`에 저장**해두고 처음 보는 업소만 받는다. 회당 상한(`NAVER_TEL_MAX_PER_RUN`)을 넘으면 나머지는 다음 실행에서 이어받는다.

- 쿠키가 만료되거나 차단 응답을 받으면 **세션을 새로 발급받아 자동 재시도**한다.
- 429를 만나면 그 실행의 전화 수집만 접는다. **『매물장』 적재는 그대로 진행된다.**
- `office_tel_cache.json`은 지워도 된다. 다음 실행부터 다시 채워진다(며칠에 걸쳐).

### 업소전화는 며칠에 걸쳐 채워진다 (고장이 아니다)

전화는 **매물이 아니라 중개업소 단위**로 받아 캐시에 쌓는다. 회당 상한이 있어 처음에는
일부만 채워지고, 매일 실행하면서 조금씩 늘어난다.

| | 업소전화가 찬 매물 |
|---|---|
| 첫날 | 일부만 (상한만큼) |
| 며칠간 | 매일 증가 |
| 캐시가 다 찬 뒤 | 전량 유지 — 신규 업소만 가끔 |

- 감시단지 2곳 기준 중개업소가 **약 46곳**이고 상한이 10이므로 **나흘쯤** 걸린다.
  단지를 추가하면 그만큼 늘어난다.
- 채워지는 동안에도 **나머지 15개 컬럼은 첫날부터 완전하다.** 배치 2는 업소전화를
  판정에 쓰지 않으므로 알림도 정상이다.
- 유선번호를 등록하지 않은 업소는 휴대폰 번호가 들어간다. 목록 API에는 전화가 아예
  없어 상세 페이지에서 받는데, 그 페이지에 유선이 없으면 휴대폰만 있기 때문이다.
- **빨리 채우려고 수동 실행을 반복하지 않는다.** 아래 주의사항 참고.

## 감시단지 등록

수집 대상은 『설정』 시트의 표로 정한다. **1행이 헤더, 2행부터 단지 하나당 한 행**이다.

| | A 감시단지 | B 네이버단지코드 | C 법정동코드 | D 관리여부 |
|---|---|---|---|---|
| 2 | 삼익맨션(삼익가든) | 1304 | 1174010100 | 관리 |
| 3 | 고덕주공9단지 | 1314 | | 관리 |

- 추가할 때는 **맨 아래 행에 이어 쓴다.** A열(단지명)과 B열(단지코드)만 채우면 된다.
- `네이버단지코드` — 네이버 부동산 단지 URL의 숫자. 비면 그 행만 건너뛰고 경고를 남긴다.
- `법정동코드` — 10자리. **수집에는 쓰지 않는다.** 나중 공공데이터 연계를 위한 자리이니 비워도 된다.
- `관리여부` — `삭제`로 바꾸면 그 단지는 감시에서 빠진다. **행을 지우지 말고 이 값으로 끈다.**
- 표는 A·B열이 **모두** 빈 행에서 끝난다. 중간에 빈 행을 두면 그 아래는 읽지 않는다.
- A열에 `단지명|단지코드`를 통째로 붙여 넣은 예전 형식도 그대로 받아준다.

> ⚠️ 『설정』은 **배치 1과 배치 2가 함께 읽는 탭**이다. 열 이름과 순서는 두 배치의 약속이므로
> 한쪽만 보고 바꾸면 안 된다. 실제로 2026-08-04에 이 탭 형식을 한쪽만 바꿨다가 배치 2가
> 감시단지를 하나도 못 읽어 알림이 조용히 멈춘 적이 있다. 바꿔야 한다면 두 저장소를
> 함께 고치고 양쪽 실행을 확인한다.

## 『실행로그』 탭

배치가 돌았는지 **PC 앞에 앉지 않고 시트에서 확인**하기 위한 탭. 실행 1회당 감시단지 1행씩 누적된다.

| 실행시각 | 배치 | 단지코드 | 단지 | 결과 | 수집매물 | 적재행수 | 소요초 | 메시지 |
|---|---|---|---|---|---|---|---|---|

- `결과` — 단지별 `성공` / `매물없음` / `실패`. 실행 전체가 중단된 경우 단지 칸이 `(전체)`인 `중단`·`실패` 행이 한 줄 붙는다.
- `적재행수`는 매물번호 중복 제거 후 실제 『매물장』에 들어간 행 수다. `수집매물`과 다를 수 있다.
- **실패한 날도 반드시 기록된다.** 행이 아예 없는 날 = 배치가 실행조차 되지 않은 날(PC 꺼짐 등)로 읽으면 된다.
- 로그 쓰기 실패는 경고만 남기고 배치를 중단시키지 않는다. 반대로 『매물장』 적재 실패는 그대로 중단한다.
- 시트 인증 자체가 깨진 날은 시트에 남길 수 없다. 그때의 진단 수단은 로컬 `logs\batch1.log`이므로 **파일 로그도 계속 유지한다.**
- `--dry-run` 은 실행로그도 쓰지 않는다.

## 실행

평소에는 **윈도우 작업 스케줄러가 매일 08:00에 자동 실행**한다(작업 이름 `네이버매물수집_배치1`).
직접 돌릴 일은 거의 없다. 배치 2보다 **먼저** 실행되어야 한다.

수동으로 돌려야 한다면 래퍼를 쓴다. 결과가 `logs\batch1.log`에 이어 붙는다.

```
run_batch1.bat
```

개발·점검용으로는 가상환경의 파이썬을 직접 부른다.

```bash
.venv\Scripts\python.exe main.py            # 수집 → 『매물장』 전량 교체 적재
.venv\Scripts\python.exe main.py --dry-run  # 시트에 쓰지 않고 변환 결과만 출력
```

> `--dry-run`은 『매물장』도 『실행로그』도 건드리지 않지만 **네이버 요청은 실제로 나간다.**
> 차단 위험은 똑같으니 연달아 돌리지 않는다.

## 사용자 주의사항

- 본 배치가 **먼저** 실행되어야 한다. 수집이 돌지 않은 날은 알림이 나가지 않는다.
- 로컬 실행이므로 **PC가 켜져 있어야 한다.** (아래 「PC 전원 상태별 동작」 참고)
- 『매물장』 시트를 직접 편집하지 않는다. 매 실행 시 전량 교체된다.
- 『실행로그』는 자동 정리 없이 계속 누적된다. 필요하면 오래된 행만 직접 지운다. (헤더는 지워도 다음 실행에 복구된다)
- 주기를 바꿀 때는 **알림 배치와 함께 조정한다.** 수집만 늘려도 알림은 하루 한 번이다.
- 인증 키 파일(`*.json`)과 `.env`가 저장소에 포함되지 않도록 주의한다.
- 수집에 걸리는 시간을 한 번 재보고 알림 배치 시각을 조정한다. (기본 간격 30분)

### ⚠️ 짧은 시간에 여러 번 수동 실행하지 않는다

네이버는 요청이 몰리면 HTTP 429로 막는데, **한 번 걸리면 몇 시간씩 풀리지 않는다.**

- 2026-08-05 실측: **약 50요청 / 28초**에서 걸렸고, **3시간 41분** 뒤에도 여전히 막혀 있었다.
  (다음 날 아침에는 풀려 있었다.)
- **IP 기준이고 네이버 부동산 전체에 걸린다.** 수집 방식을 바꾸거나 다시 실행해도 안 풀린다.
  기다리는 것 말고는 방법이 없다.
- 조용히 기다린다고 더 빨리 풀리지도 않는다. 그냥 차단이 길다.
- 정상 실행 1회는 **약 17요청 / 28초**로, 걸렸던 양의 3분의 1이다. 하루 한 번은 안전하다.

막힌 날은 『매물장』이 **직전 데이터 그대로 보존**되고 『실행로그』에 실패가 남는다.
시트가 깨지지는 않으니 다음 날 정기 실행을 기다리면 된다.

### PC 전원 상태별 동작

로컬 실행이라 PC 상태에 따라 수집 여부가 갈린다.

| 상태 | 수집 |
|---|---|
| 화면 잠금 (Win+L) | ✅ 된다 |
| 모니터 절전 · 화면 꺼짐 | ✅ 된다 |
| 로그오프 / 사인아웃 | ❌ 안 된다 |
| 절전(Sleep) · 최대절전(Hibernate) | ❌ 안 된다 |
| 종료(Shutdown) | ❌ 안 된다 |

- 자리를 비울 때는 **로그아웃 말고 잠금(Win+L)만** 한다.
- PC가 꺼져 있었다면 다음에 켤 때 밀린 실행이 따라 돈다. 다만 **그 시각이 알림 배치보다
  늦으면 그날 알림은 건너뛴다.**
- 주말·휴가처럼 며칠 안 켜면 그 기간 수집은 없다.
- 절전 상태에서도 돌리고 싶으면 작업 스케줄러에서 **"절전 해제하고 실행"**을 켠다.
  (종료 상태에는 무효)
