> 관심 단지의 매물을 수집해 구글시트 『매물장』에 적재하는 배치

| | |
|---|---|
| **문서** | `PRD_배치1_매물수집적재.md` — 본 문서 |
| **짝 문서** | `PRD_배치2_시세분석알림.md` — 분석·알림 사양 |

## ⚠️ 이 문서의 성격

**본 문서는 신규 개발 사양이 아니다.**

수집 로직은 이미 구현되어 정상 동작하고 있다. 본 문서가 정의하는 것은 **그 결과를 구글시트에 적재하는 계층**과, 배치 2가 읽을 수 있도록 지켜야 할 **계약 조건**뿐이다.

### 수정 금지 파일

아래 파일은 **읽기만 하고 수정하지 않는다.** 리팩터링·재작성·구조 변경 모두 해당한다.

```
naver_client.py     네이버 매물 수집 클라이언트 — 수정 금지
main.py             기존 실행 진입점 — §2.3 참조
```

`naver_client.py`가 반환하는 데이터 구조를 **있는 그대로 받아서** 시트 스키마로 변환한다. 반환 형태가 마음에 들지 않아도 클라이언트를 고치지 말고, 변환 계층에서 처리한다.

### 신규 작성 파일

```
sheets_loader.py    구글시트 적재 — 신규
field_mapper.py     수집 결과 → 시트 스키마 변환 · 정규화 — 신규
```

### 참고만 하는 파일

프로젝트 루트의 `test_*.py`는 개발 중 작성된 실험 스크립트다. **동작을 이해하기 위한 참고 자료로만 보고, 수정하거나 실행 흐름에 포함하지 않는다.**

```
test_click_correct.py    test_real_click_fetch.py
test_realtor_phone_fix.py    test_realtor_keys.py
test_playwright.py    test_nnb.py
test_endpoints.py    test_mobile.py
```

### 기존 산출물

루트의 `네이버부동산_매물목록_*.xlsx` 파일들은 기존 엑셀 출력 결과다. **필드 구조 확인용 참고 자료**이며, 새 코드는 엑셀을 생성하지 않는다.

## 1. 개요

### 1.1 시스템 구성

```
[배치 1]  본 문서
          로컬 PC · 작업 스케줄러 · 08:00
          매물 수집 → 『매물장』 시트에 적재
                          │
                    구글시트가 유일한 접점
                          │
[배치 2]  PRD_배치2_시세분석알림.md
          GitHub Actions · 08:30
          『매물장』 읽기 → 분석 → 『시세이력』 기록 → 카톡
```

두 배치는 서로를 호출하지 않는다. 시트를 통해서만 이어지므로 각각 독립적으로 수정할 수 있다.

### 1.2 변경 내용

```
기존:  main.py → naver_client.py 수집 → 엑셀 파일 출력
변경:  main.py → naver_client.py 수집 → field_mapper → sheets_loader → 시트 적재
```

**엑셀 출력은 사용하지 않는다.** `naver_client.py`는 그대로 두고, 그 결과를 받는 뒤쪽만 교체한다.

### 1.2.1 `main.py` 처리

기존 진입점의 **수집 호출 부분은 유지**하고, 엑셀 출력 부분만 시트 적재로 교체한다. 파일을 새로 만들지 말고 해당 구간만 수정한다.

```python
# 유지
listings = naver_client.fetch(...)

# 교체 — 엑셀 출력 제거, 아래로 대체
rows = field_mapper.to_sheet_rows(listings, run_at)
sheets_loader.replace_all(rows)
```

### 1.3 범위

| 포함 | 제외 |
|---|---|
| 구글시트 인증 | 수집 로직 수정 |
| 『매물장』 전량 교체 | 데이터 분석·판정 |
| `수집일시` 기록 | 카톡 발송 |
| 개인정보 필드 제외 | 시세이력 관리 |
| 감시단지 목록 읽기 | |

## 2. 『매물장』 스키마

**배치 2와의 계약이다. 컬럼명과 순서를 임의로 변경하지 않는다.**

| 컬럼 | 타입 | 설명 |
|---|---|---|
| `매물번호` | text | 원천 고유번호 |
| `단지코드` | text | 네이버 단지코드 |
| `단지` | text | 표시용 단지명 |
| `거래유형` | text | `매매` / `전세` / `월세` |
| `동` | text | 예: `101동` |
| `층원문` | text | 원천 표기 그대로. `고/10`, `8/10` 등 |
| `층대` | text | 정규화 결과. `저층` / `중층` / `고층` |
| `평형` | text | 공급면적 ㎡ 정수. 예: `112` |
| `가격` | number | **만원 단위 정수.** 매매가 또는 보증금 |
| `월세` | number | 만원 단위 정수. 매매·전세는 `0` |
| `향` | text | 예: `남향` |
| `중개업소` | text | 업소명 |
| `업소전화` | text | 업소 대표전화 |
| `묶음수` | number | 원천이 제공하는 동일매물 묶음 개수 |
| `매물링크` | text | |
| `수집일시` | text | **ISO 형식. 완료 신호로 사용됨** |

### 2.1 개인정보 제외

다음 필드는 **수집하지 않으며 시트에도 기록하지 않는다.**

- 중개사 개인 휴대폰 번호
- 중개사 대표자명
- 중개업소 주소

연락은 업소 대표전화로 충분하다. 배포 도구 특성상 사용자 시트에 동종업계 종사자의 개인정보가 누적되는 것을 피한다.

### 2.2 정규화 책임

수집 결과를 그대로 쓰지 않고, 아래 두 가지는 **배치 1이 처리해 적재한다.**

**층 정규화** — 원천의 층 표기에 두 형식이 섞여 들어온다.

```
"고/10", "저/12", "중/15"   ← 층대 표기
"8/10",  "11/11", "4/12"    ← 실층수 표기
```

```
앞부분이 저/중/고  → 그대로 사용
앞부분이 숫자      → 총층 대비 비율로 환산
                     ~1/3 저층 / ~2/3 중층 / 그 이상 고층
```

원문은 `층원문`에, 정규화 결과는 `층대`에 각각 기록한다.

**가격 파싱** — 문자열을 만원 단위 정수로 변환한다.

```
"17억 5,000"  → 175000
"7억"         → 70000
"1억"         → 10000
```

## 3. 계약 조건

배치 2가 정상 동작하려면 아래 네 가지를 반드시 지켜야 한다.

### 3.1 전량 교체

매 실행 시 『매물장』의 **기존 행을 전부 삭제한 뒤 재삽입한다.**

- 헤더 행은 유지한다.
- 부분 갱신·append 하지 않는다.
- 소진된 매물을 판별해 지우려 하지 않는다. 전량 교체가 그 역할을 대신한다.

### 3.2 `수집일시` — 완료 신호

**모든 행에 동일한 실행 시각을 기록한다.** 행마다 다른 시각을 넣지 않는다.

```python
run_at = datetime.now().isoformat(timespec="seconds")
# 모든 행에 동일하게 기록
```

배치 2는 이 값이 당일이 아니면 분석을 중단한다. 따라서 **이 값은 "이 데이터는 오늘 수집된 것"이라는 보증**이며, 수집이 정상 완료된 경우에만 기록되어야 한다.

### 3.3 원자적 적재

**부분 적재 상태로 종료하지 않는다.**

수집이 중간에 실패하면 시트를 건드리지 않고 종료한다. 절반만 적재된 상태로 배치 2가 읽으면 매물수가 급감한 것으로 오인해 오탐이 발생한다.

```
전 단지 수집 성공 → 전량 교체 실행
일부 단지만 실패  → 성공한 단지만 적재, 실패 단지는 로그
전 단지 실패      → 시트 미변경, 종료
```

### 3.4 실행 순서

배치 2보다 **먼저** 실행되어야 한다. 기본 간격은 30분이다.

```
08:00  배치 1  수집 → 적재
08:30  배치 2  읽기 → 분석 → 발송
```

수집 소요 시간이 길어 30분을 넘기면 간격을 늘린다. 순서가 어긋나면 배치 2가 신선도 검증에서 걸러내므로 오탐은 없으나, 그날 알림은 나가지 않는다.

## 4. 감시단지 목록

배치 1은 『설정』 시트의 `감시단지` 값을 읽어 대상을 정한다.

```
삼익맨션(삼익가든)|12345
고덕그라시움|67890
```

- 형식은 `단지명|단지코드`. 줄바꿈 또는 쉼표로 복수 등록
- 단지명은 표시용, 실제 조회 키는 **단지코드**
- 형식이 잘못된 행은 건너뛰고 로그를 남긴다

> 두 배치가 같은 『설정』 시트를 읽는다. 사용자가 단지를 추가하면 양쪽에 자동 반영된다.

## 8. 실행 환경

### 8.1 스택

- Python 3.11+
- `playwright` — 기존 수집 로직이 사용 중. **브라우저 바이너리 별도 설치 필요**
- `gspread` — 구글시트

```bash
pip install -r requirements.txt
playwright install chromium     # 이 단계를 빠뜨리면 실행되지 않는다
```

> `pip install playwright`만으로는 동작하지 않는다. 브라우저 바이너리를 받는 두 번째 명령이 반드시 필요하며, **설치 안내에서 가장 자주 누락되는 지점이다.**

### 8.2 스케줄

윈도우 작업 스케줄러에 등록한다. 기본 08:00.

- 로컬 실행이므로 **PC가 켜져 있어야 한다**
- 배치 2보다 먼저 실행되도록 시각을 맞춘다

**소요 시간을 실측해 간격을 정한다.** 브라우저 기반이라 단지 수에 비례해 시간이 늘어난다. 기본 간격 30분이 빠듯하면 배치 2를 뒤로 미룬다. 배치 1이 끝나기 전에 배치 2가 돌면 그날 알림은 나가지 않는다.

**헤드리스 모드를 권장한다.** 그렇지 않으면 매일 아침 브라우저 창이 화면에 뜬다.

### 8.3 로컬 테스트

시트 적재 없이 결과만 확인할 수 있는 `--dry-run` 옵션을 둔다. 개발 중 시트를 오염시키지 않기 위함이다.

## 10. 사용자 주의사항 (README에 포함)

- 본 배치가 **먼저** 실행되어야 한다. 수집이 돌지 않은 날은 알림이 나가지 않는다.
- 로컬 실행이므로 **PC가 켜져 있어야 한다.**
- 『매물장』 시트를 직접 편집하지 않는다. 매 실행 시 전량 교체된다.
- 주기를 바꿀 때는 **알림 배치와 함께 조정한다.** 수집만 늘려도 알림은 하루 한 번이다.
- 인증 키 파일이 저장소에 포함되지 않도록 주의한다.
- 설치 시 `playwright install chromium`을 반드시 실행한다. 이 단계를 빠뜨리면 수집이 시작되지 않는다.
- 수집에 걸리는 시간을 한 번 재보고 알림 배치 시각을 조정한다.

## 11. 향후 확장 (범위 밖)

- 클라우드 실행 — PC 의존을 없앨 수 있으나, 실행 IP 대역과 코드 공개 범위를 함께 고려해야 한다.
- 수집 주기 세분화 — 오후 등록 매물을 당일 잡으려면 주기를 늘려야 하나, 그만큼 원천 요청량도 비례해 늘어난다.
